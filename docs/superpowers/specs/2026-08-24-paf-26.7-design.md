# Move the PoC to Private Agent Factory 26.7

**Date:** 2026-08-24
**Status:** DESIGN — approved, not yet implemented.
**Branch:** `paf-26.7`

## Problem

The PoC is built against PAF 26.4 and the stack is down. Three of the ten product
gaps in `issues/` are fixed in 26.7, and the workarounds they forced are still
carried in the repository:

- `paf/patches/agentstep-unique-tool-names.sh` rewrites `AgentStep.py` inside the
  running container so each Agent node registers a unique tool name. 26.7 ships
  the same fix upstream (`AgentStep.py:278` `_runtime_tool_name()` returning
  `AgentStep_<sha256[:12]>`), and the patch's anchors no longer exist — it aborts
  with `SystemExit` instead of applying.
- `manage.py` builds a CA bundle and appends the MCP gateway certificate to
  `certifi`'s `cacert.pem` inside the container, because `SSL_CERT_FILE` never
  reached PAF's MCP discovery worker. 26.7's `MCPClient` builds its HTTP clients
  through `tls_utils.create_httpx_client` / `create_async_httpx_client`, which
  load an administrator-supplied bundle from `/mount/config/app/latest/certs/`.
  The bundle is uploaded through an API and lives on a mounted volume.
- `PafClient` authenticates with an admin session cookie, sniffs response bodies
  for HTML to detect a `303` redirect to the login page, and re-logs-in on
  expiry. 26.7 raises `HTTPException(401)` from `async_require_authenticated_user`
  and adds `POST /v1/integrations/agents/{agent_id}/run`, authenticated by a
  Bearer API key bound to one published agent.

Rebuilding the environment on 26.4 would re-create all three. This work moves the
repository to 26.7, deploys a fresh instance, and validates the result.

## Decisions

**Single pass.** All changes land on one branch and one deployment, rather than a
parity-first baseline followed by adoptions. Each PAF image build costs ten
minutes or more; the harness is the arbiter either way.

**MCP stays behind TLS.** MCP servers keep their `https://mcp-proxy:8443/<svc>/mcp/`
URLs through the Caddy gateway. PAF would accept plain `http` — `ALLOW_INSECURE_HTTP_URLS`
defaults to true and `mcp_server_blueprint._validate_mcp_outbound_url` never
enforces `https` — but a private deployment that terminates TLS between the agent
platform and its tools is part of what the PoC demonstrates. Keeping TLS is also
what gives the certificate API something to do.

**`MAX_AGENT_ITERATIONS = 8`.** 26.7 still caps agent iterations at 5
(`AgentStep.py:161`) with no setting to change it. A container patch raises it to
8: enough headroom for the four-call `EvaluationAgent` recipe plus a retry,
without letting a confused agent spend a long tool loop on every turn.

**`manage.py` mints the API key.** A `paf api-key` command authenticates as
administrator once, creates the key, and writes it to `.env`. Administrator
credentials stay in the operator's tooling; the Spring backend holds only an
agent-scoped key.

**`docs/superpowers/specs/` is out of scope for the documentation cleanup.** It is
a dated record of design decisions, not a description of the current system. Every
other document describes the deployment as it is, with no version narration.

## Change inventory

### `manage.py`

Remove the certificate injection: the `KIT_CERTIFI` and `PAF_CERTIFI_IN_CONTAINER`
constants, the trust-bundle build inside `_configure_mcp_tls`, and
`_inject_mcp_ca_into_paf`. Gateway certificate _generation_ stays — only the
injection into the image goes. Remove `SSL_CERT_FILE` from the compose
environment.

Add `paf trust-ca`: authenticate as administrator, upload the MCP gateway CA with
`POST /agentFactory/v1/certs` as multipart form field `certificate`. `201` means
added, `200` means already present.

Add `paf api-key`: resolve the `CHAT_WORKFLOW` agent id, `POST /v1/integrations/agents/{id}/keys`,
and write `PAF_AGENT_ID` and `PAF_API_KEY` into `.env`. Keys carry a maximum
90-day lifetime (`INTEGRATION_KEY_MAX_TTL_DAYS`); the command is re-runnable to
mint a replacement.

`paf allow-internal-mcp` is unchanged. The outbound-URL policy is identical in
26.7, and a fresh install restores `BLOCK_PRIVATE_OUTBOUND_URLS` to its secure
default, so the command is still required.

### `paf/patches/`

Delete `agentstep-unique-tool-names.sh`. Add a patch that sets
`MAX_AGENT_ITERATIONS = 8` in `AgentStep.py`: idempotent, verified with
`py_compile`, followed by `manage_app.sh`. It runs after every image build and the
deployment guide lists it as an ordinary step.

### `src/backend`

`PafClient` loses `login()`, `ensureCookie()`, `postRunWithSessionRetry()`,
`looksLikeJson()`, `discoverAgentId()` and the `Origin` header. It becomes a
single `POST` to `/agentFactory/v1/integrations/agents/{agentId}/run` carrying
`Authorization: Bearer <key>`, reading `paf.api-key` and `paf.agent-id` from
configuration. `paf.admin-user` and `paf.admin-pass` are removed.

The endpoint returns a typed error envelope, `{"error": {"code", "message"}}`, so
failures map by code rather than by body shape:

| Code                                        | Status | Handling                                    |
| ------------------------------------------- | ------ | ------------------------------------------- |
| `INTEGRATION_KEY_INVALID`                   | 401    | 502 to the caller; the key is wrong         |
| `INTEGRATION_KEY_EXPIRED`                   | 401    | 502 with a log line naming `paf api-key`    |
| `INTEGRATION_KEY_INACTIVE`                  | 401    | 502; key or owner disabled                  |
| `INTEGRATION_KEY_NOT_AUTHORIZED_FOR_TARGET` | 403    | 502; wrong agent or missing `run` scope     |
| `INTEGRATION_AGENT_NOT_PUBLISHED`           | 400    | 502 with a log line naming the publish step |

The success body is `{"roomId", "message"}`, unchanged, so `Envelope` and its
tests are untouched. `PafClientTest` is rewritten against Bearer auth and the
error codes.

### `paf/flows/`

Conditional on validation. 26.7's `AgentBuilder` collects several edges arriving
at one input into a fan-in list (`_collect_fanin_groups`) and skips data-flow
edges aimed at inputs a node does not have (`_component_has_input`). If the canvas
confirms both, the `CHAT_WORKFLOW` condition gates drop the workaround that
forwards the session token through a branch's `True Message`, and the flow is
re-exported with `CHAT_WORKFLOW.md` updated to match. If the canvas does not
confirm them, the flow is unchanged and the finding is recorded in `issues/`.

### Documentation

`LOCAL.md`, `PAF.md`, `TROUBLESHOOT.md`, `BACKLOG.md`, `README.md` and `DEMO.md`
describe the 26.7 deployment as the only one that has existed. No upgrade
narration, no "26.4 required", no changelog entries. Concretely:

- `LOCAL.md`: the certificate step becomes the `paf trust-ca` upload; the API key
  step is added after publishing the flow; the tool-name patch step is gone and
  the iteration patch takes its place.
- `PAF.md`: the integration endpoint replaces the cookie-and-`agentBuilder/run`

- `TROUBLESHOOT.md`: entries whose cause 26.7 removed are deleted, not annotated.
- `BACKLOG.md`: items 0.1–0.4 are re-cut against what remains open. Item 0.3 is

## Deployment sequence

Follows `LOCAL.md`'s existing shape, with the certificate, patch and key steps in
their new places:

1. `local down --purge`
2. `setup local`, pointing `PAF_TARBALL` at the 26.7 kit
3. `paf prepare`, `paf build`
4. `local up` — boots the stack, runs Liquibase, generates the MCP gateway
   certificate and starts `mcp-proxy`
5. `paf bootstrap`, then the PAF install wizard in the browser. The wizard offers
   an optional multi-worker step (`DBMS_AQ` grant plus `AAI_SOCKETIO_QUEUE`) that
   this single-worker deployment skips
6. `paf allow-internal-mcp`
7. `paf trust-ca` — uploads the gateway CA so PAF trusts the MCP URLs
8. Apply the iteration patch (it restarts the PAF application)
9. Register the five MCP servers, the Banking Application DB datasource and the
   Company Registry REST source
10. Import and publish `CHAT_WORKFLOW`
11. `paf api-key`
12. `podman compose -f deploy/podman/compose.local.yml up -d --force-recreate --no-deps application-backend`
    so `application-backend` picks up `PAF_AGENT_ID` and `PAF_API_KEY` (its environment is fixed at
    container creation, so a plain `podman restart` would keep it empty)

## Risks

**Importing the 26.4 `.paf` archive into 26.7 is untested.** If it fails or the
imported flow misbehaves, the fallback is rebuilding `CHAT_WORKFLOW` from
`paf/flows/CHAT_WORKFLOW.md`, which is documented but costs roughly an hour.

**Deterministic MCP node behaviour may change on load.** `AgentBuilder._normalize_runtime_node_flags`
rewrites `passInlineData` on MCP tool-runner nodes, which previously caused
downstream Chat output nodes to run with an empty `message`. Expect the flow to
behave differently, not identically. This is why the harness runs before any flow
edits.

**The iteration patch is image-level** and must be re-applied after every image
build.

**The agentic `upsert_application` write path still carries the streamed-token
corruption risk.** Nothing in 26.7 addresses it. It remains a caveat of the PoC.

**Manager/worker reply selection differs from the retired patch.** 26.7 returns the
last worker's `tool_result` (`AgentStep.py:1365-1382`) rather than the manager's
`talk_to_user` text. `CHAT_WORKFLOW` uses sequential agents rather than
sub-agents, so this should not apply — but any node with sub-agents wired needs
re-checking.

## Out of scope

**Agent Memory stays off.** Memory is scoped to a _(PAF user, workflow)_ pair, and
an integration key runs every request as the user who created it. Enabling memory
would place every bank customer's conversation under one PAF user, where "share
memory between chat threads" makes one customer's details retrievable in another
customer's chat.

The remaining 26.7 additions — A2A, Vision LLM, Image Input, URL Crawler, Jira,
the Deep Data Research and Data Analysis nodes, Agent Spec export — are not part
of this work.
